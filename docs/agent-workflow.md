# Руководство для AI-агента

Агент работает со студией только через MCP-сервер (`studio mcp`, см. [mcp.md](mcp.md)) и
находит студию сам. Этот текст сервер отдаёт клиенту как инструкции при подключении, а
команда `studio skill` устанавливает его в проект: как скилл Claude Code
(`.claude/skills/pacage-studio/SKILL.md`) и/или как блок в `AGENTS.md`. Источник —
`studio/agent/guide.md`; ниже его копия (совпадение проверяет тест).

# Работа AI-агента со студией (pacage-studio) через MCP

Студия — локальный сервис с картой проекта на `fastbase` / `core-package` /
`event-infra` (endpoint → scenario → io → model) и вкладкой фронтенда. Человек ведёт работу
в её интерфейсе по **дорожной карте** (синхронизация → режим → идеи → валидация → перенос →
выбор задач → реализация → отчёт), ты — через инструменты MCP. **Решения всегда за
человеком**: ты предлагаешь и реализуешь то, что он выбрал, ничего не применяешь за него.

## 1. Подключение

Вызови `studio_connect()` **без параметров**: студия находится сама (в проекте её файл
`.studio/server.json`), ничего копировать человеку не нужно. Ответ — версия студии, корень
проекта и текущий этап. Дальше работай циклом из раздела 2.

- `studio_not_running` — студия не запущена: попроси человека выполнить `studio` в проекте.
  Если MCP-сервер запущен не из папки проекта, нужна переменная `STUDIO_PROJECT`.
- `bad_token` после перезапуска студии — просто вызови `studio_connect()` снова.
- Запасной путь для особых случаев: строка из окна «AI-агент» целиком —
  `studio_connect(connection=<строка>)`.
- Токены не записывай в файлы проекта, коммиты и логи.
- Если файл скилла или блок `AGENTS.md` помечен версией `pacage-studio X`, а
  `studio_version` в ответе новее, скажи человеку выполнить `studio skill`.

Любой инструмент, вызванный до подключения, вернёт `not_connected`.

## 2. Цикл: `studio_workflow`

`studio_workflow(wait_seconds=20)` — главный инструмент. Он возвращает `stage` (этап),
`task` (задача человека), `action` и `instruction`. Действуй по `action`:

| action | что значит | что делать |
|---|---|---|
| `wait` | человек ещё не дошёл до твоего этапа | вызови `studio_workflow` снова (он сам ждёт до 25 с) |
| `propose` | этап «Идеи агента» | раздел 3 |
| `implement` | этап «Реализация» | раздел 4 |

Если несколько минут подряд `action=wait`, скажи человеку, чего ждёшь (`instruction`), и
остановись: он вернёт тебя к работе. **Если тебя запустила сама студия** (так сказано в запросе),
выполни только текущий этап и заверши работу — не вызывай `studio_workflow` в цикле: студия
запустит тебя снова, когда понадобишься. Запись, не подходящая текущему этапу, студия
отклонит (`stage_forbidden`) — это не ошибка, а просьба подождать.

## 3. Идеи (`action=propose`)

Цель — подготовить карточки, которые человек будет валидировать свайпом (вверх — принять,
вниз — отклонить). Код не пиши.

1. Изучи проект: `studio_overview`, `studio_graph` (фильтры `kind`, `query`,
   `planned_only`), `studio_node`, `studio_frontend`, `studio_ideas`. Не дублируй
   существующие эндпоинты, сценарии, страницы и идеи. Учти `task` из дорожной карты.
2. Пришли идею: `studio_idea_add(title, description, scenarios, pages)`:
   - `scenarios` — сценарии бэкенда: `{title, slug, description, acceptance[], domain,
     http_method, path, uses_db, with_test}`. `slug` — **snake_case латиницей**, он станет
     именем кода (`list_lessons` → `ListLessonsScenario`, функция `list_lessons`); по
     названию на другом языке slug не выводи — задай его сам. `http_method` и `path`
     обязательны.
   - `pages` — только если задача затрагивает интерфейс: `{title, name (kebab-case),
     description, acceptance[], domain (роль), route, calls[«GET /path»], blocks[{name
     (PascalCase), description, acceptance[], calls[]}]}`.
   Каждый сценарий и страница станут отдельными карточками. Студия проверяет slug и
   конфликты сразу; при ошибке (`invalid_input`) прочитай сообщение, исправь и отправь снова.
3. Идей может быть несколько. Когда достаточно — `studio_ideas_ready()`: человек перейдёт к
   валидации. Дальше вернись к `studio_workflow`.

`calls` — какие эндпоинты бэкенда вызывает страница (`МЕТОД /путь`); они должны существовать
или быть среди присланных сценариев.

## 4. Реализация (`action=implement`)

Человек отметил задачи и сохранил ТЗ. Делай только их.

1. Читай ТЗ **по частям** — целиком оно бывает на десятки тысяч символов и не помещается в
   ответ. `studio_brief(part="backend")` и/или `studio_brief(part="frontend")` (какие части
   есть — в поле `briefs` ответа `studio_workflow`) вернут оглавление: задачи (номер, имя,
   размер) и разделы. Прочитай правила один раз (`studio_brief(section="2")` и `"3"`), затем
   берись за задачи по одной: `studio_brief(task=N)`. Если ответ обрезан, продолжи с
   `offset=next_offset`. Правила внутри ТЗ главнее этого текста. В ТЗ упомянуты команды CLI:
   `studio verify` для тебя — `studio_verify`, `studio doctor --strict` — `studio_doctor`.
2. Реализуй задачи в коде. Не трогай `.env*`, `.studio/` и конфигурацию, не коммить без
   просьбы, не меняй то, что не входит в ТЗ. Сначала бэкенд, потом фронтенд.
3. Запусти тесты проекта и зафиксируй результат.
4. Проверь по коду: `studio_verify(part)` и `studio_doctor(strict=true)`. `studio_verify`
   смотрит на **структуру** (есть ли слои, связи и тест с нужным именем), но не на критерии
   приёмки и поведение: статус `выполнено` не заменяет тесты, а `частично` и `не сделано`
   перечисляют в `items[].message`, чего не хватает. Исправляй и проверяй снова.
5. Отчёт: `studio_report(summary, part, updates, not_synced, report)`.
   - `summary` — **главное**: понятный человеку текст без жаргона: что сделано, что
     проверено (тесты, `studio_verify`), что осталось или требует его решения.
   - `updates` — необязательно: описания реализованных узлов `[{id, description,
     acceptance[]}]` (для планов бэкенда `{plan, layer, description, acceptance[]}`);
     `not_synced` — `[{id, reason}]`; `report` — `{outside_changes[], tests, questions[],
     decisions[]}`. В ответе `rejected` перечисляет отклонённые записи и причины.
   После отчёта цепочка переходит на этап «Отчёт»: человек читает его и либо завершает цикл,
   либо возвращает к выбору задач. Статусы отчётов — `studio_reports`.

## 5. Общие правила

- Неоднозначная задача — спроси человека, не додумывай. Не выдумывай эндпоинты, модели и
  поля: сверяйся с графом.
- На этапах без твоей записи (валидация, перенос, выбор) ничего не делай, только жди.
- Отказ студии (`mode_forbidden`, `stage_forbidden`) намеренный: не обходи его, сообщи
  человеку, что именно запрещено, и предложи другой путь.
- Каждое действие должно быть понятно человеку: называй, что собираешься делать.
