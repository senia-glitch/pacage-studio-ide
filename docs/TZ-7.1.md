# ТЗ для пакета: задания на версию 7.1

**Статус: реализовано в 7.1.0** (см. `CHANGELOG.md`). Решения, согласованные при обсуждении:

1. «Уже есть в коде»: карточку не переносим, а помечаем (`inCode`, бейдж, группа «Реализованные»);
   остальные переносятся, принудительный перенос — по подтверждению.
2. Имена из `slug`: причина была в том, что свайп вверх и «На карту ↗» создавали `studio:*`-узлы
   прямо из заголовка; теперь они идут через серверный перенос по `slug`.
3. План → факт: описание уходит на реальные узлы, запись плана удаляется, остаётся журнал.
4. Окружение агента: только автоматически (`.venv`/`venv`), без ручной замены в настройках.

Четыре пункта, записанные после первого реального прогона цикла «агент → дорожная карта».
Порядок — по важности. Ссылки на код указывают, где сейчас находится нужное место.

## 1. Сверка карточек с кодом перед переносом

**Проблема.** «Перенос на карту» (`chain.transfer`, `studio/server/chain.py`) превращает
принятые карточки в планы и плановые страницы, не проверяя, есть ли эта функциональность в
коде. Агент мог предложить то, что уже реализовано, и на карте появляются дубли.

**Требование.**
- Перед переносом студия сверяет каждую принятую карточку с графом бэкенда и фронтенда:
  совпадение по маршруту (`http_method` + `path`, с нормализацией параметров), по `slug`
  сценария, по маршруту страницы и именам блоков.
- Результат сверки по каждой карточке: «нет в коде» (переносим), «уже есть в коде»
  (не переносим, показываем узел), «частично» (переносим только недостающее).
- «Уже есть» не блокирует остальной перенос; пользователь видит список и может перенести
  такую карточку принудительно.
- Сверка — чистая функция «карточка + граф → вердикт», без записи на диск; тесты на каждый
  вердикт. Существующие проверки конфликтов (`slug`, маршрут, порядок роутов) остаются.

**Готово, когда:** карточка про уже реализованный эндпоинт при переносе не создаёт план, а
показывает ссылку на существующий узел.

## 2. Имя узла из `slug`, а не из заголовка

**Проблема.** Имена узлов должны быть латинскими и стабильными. Заголовок карточки
свободный (русский, с пробелами), поэтому имена, построенные из него, нестабильны и
ломают сопоставление плана с кодом.

**Требование.**
- Имя слоя плана (endpoint, scenario, io, model, test), имя файла и имя класса берутся
  из `slug` (`plan_data` / `studio/metadata/plans.py`, `layer_name`, `pascal_case`), а не из
  `title`.
- `title` остаётся только отображаемым названием на карте и в ТЗ.
- Для страниц фронтенда то же правило: идентификатор и имя компонента — из `slug`/маршрута,
  название — отдельное поле.
- `slug` проверяется до переноса (латиница, цифры, `_`/`-`; уникальность) и показывается
  в карточке. Пустой или недопустимый `slug` — понятная ошибка до переноса, без молчаливой
  подстановки транслитерированного заголовка.

**Готово, когда:** карточка с русским заголовком и корректным `slug` даёт латинские имена
узлов, одинаковые при повторном переносе.

## 3. Автоматическое превращение плана в факт, когда код найден

**Проблема.** Статус плана (`resolve_plan`, `studio/scanner/plans.py`) вычисляется, но
плановые узлы и записи плана остаются «планом» (`planned`, `plan`) даже после появления кода.
Пользователь вручную закрывает то, что студия уже видит.

**Требование.**
- Когда `resolve_plan` возвращает `done` (все слои найдены, есть связь `dispatch` /
  `scenario_call` в коде), студия сама превращает план в факт: описание и критерии
  приёмки переносятся на реальные узлы, плановые заглушки убираются, статус плана
  фиксируется как выполненный.
- Для частично найденного плана (`partial`) факт не создаётся; показывается, каких слоёв
  не хватает.
- Превращение выполняется при пересканировании (после шага агента и при ручном «Обновить
  код»), идемпотентно, без потери пользовательских полей (`description`, `acceptance`,
  `domain`).
- Идея, у которой все карточки стали фактом, получает признак «реализовано» (группа
  «Реализованные» на странице «Генератор идей»), если пользователь принял работу.
- Изменение видно в журнале, чтобы автоматику можно было проверить и откатить.

**Готово, когда:** после того как агент написал код по плану, карта сама показывает факт,
а план не висит в списке задач на реализацию.

## 4. Запуск агента в окружении проекта, с `.venv`

**Проблема.** Студия запускает команду агента (`Runner._run`, `studio/server/runner.py`) с
окружением самой студии. Тесты проекта уже гоняются из его `.venv`
(`project_python`, `studio/agent/testrun.py`), а агент нет: он не видит зависимости проекта
и не может запустить тесты сам.

**Требование.**
- Если в проекте есть `.venv` или `venv`, процесс агента запускается с этим окружением:
  в начало `PATH` добавляется каталог `Scripts` (Windows) или `bin`, выставляется
  `VIRTUAL_ENV`, убирается `PYTHONHOME`.
- Логика поиска окружения общая с `project_python` (одно место, без копирования).
- В «Настройках агента» показывается, какое окружение выбрано (ручной замены нет: только
  автоматически).
- Если окружения нет, агент запускается как раньше, с явной пометкой в окне агента.
- Окружение не выводится в лог целиком (секреты в переменных не попадают в `runner.log`).

**Готово, когда:** агент из окна студии может выполнить `python -m pytest` и импортировать
зависимости проекта без ручной настройки.
