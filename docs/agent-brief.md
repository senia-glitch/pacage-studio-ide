# ТЗ для AI-агента

Студия собирает локальный markdown-документ из планируемых узлов с описанием
и карты проекта. Документ можно скопировать, скачать или сохранить в проект;
решение об отправке во внешний AI-сервис принимает пользователь.

## Команды

```bash
studio brief                      # .studio/agent-brief.md, весь проект
studio brief --stdout             # ТЗ в stdout, без файла ТЗ
# при --stdout и --json служебные .studio/briefs/*.json и last-brief.json
# всё равно пишутся: по ним работает studio verify
studio brief --plan cancel_order  # один план (можно повторять)
studio brief --only CancelOrder   # старый планируемый узел (можно повторять)
studio brief --scenario cancel_order --map related
studio brief --include-empty      # включить узлы без описания
studio brief --section map --section anchors   # только эти необязательные разделы
studio verify                     # проверить последнее ТЗ
studio verify .studio/agent-brief.md --json
```

## Что попадает в ТЗ

- постановка и таблица задач;
- правила работы из `studio/agent/rules.md`;
- правила проекта из `studio.rules.md`, если файл есть;
- задачи-планы: сценарий целиком — описание и критерии один раз, таблица
  цепочки слоёв, порядок реализации, что можно переиспользовать, образцы по
  слоям, решения за агентом и проверка через `studio verify`;
- старые задачи-узлы: целевой файл, якорь, домен, место в запросе, описание,
  критерии, связи, образец кода того же вида;
- карта проекта: дерево запроса, модели, тесты, неполные узлы;
- «Не готово к реализации» — планируемые узлы без описания;
- предупреждения по коду и жёлтые пометки;
- формат якорей и связей из `.studio/metadata.json`;
- «Отчёт и проверка»: команды проверки и строгий JSON-формат итогового отчёта агента.

Описания берутся только из `.studio/metadata.json`. Код проекта студия не
изменяет.

## Разделы и правка ТЗ

Необязательные разделы бэкенд-ТЗ — `map` (карта проекта), `unready` («Не готово
к реализации»), `diagnostics` (предупреждения по коду), `anchors` (формат якорей
и связей). По умолчанию включены все; `--section` (повторяемый) и флажки
«Разделы» в окне ТЗ оставляют только выбранные. Неизвестное имя — ошибка.
«Что нужно сделать», правила, задачи и формат итогового отчёта входят всегда.
Набор разделов входит в `brief_id`.

В окне ТЗ текст редактируется: «Скопировать», «Скачать» и «Сохранить в проект»
берут ваш вариант. Если в тексте пропал служебный маркер
`<!-- studio-brief: … -->` в конце, сохранение отклоняется — без него
`studio verify` не найдёт задачи. Смена параметров при несохранённых правках
спрашивает подтверждение.

## JSON-отчёт агента по ТЗ

Итоговый отчёт агента по ТЗ — тоже один JSON-блок (раздел «Отчёт и проверка»;
для ТЗ фронтенда — раздел 6). Формат тот же, что у синхронизации, с двумя
добавлениями — адресация слоя плана и блок `report`:

```json
{
  "updates": [
    {"plan": "<slug плана>", "layer": "endpoint | scenario | io | model",
     "description": "<что узел делает фактически>", "acceptance": ["<критерий>"]},
    {"id": "<якорь узла>", "description": "…", "acceptance": ["…"]}
  ],
  "not_synced": [{"plan": "<slug>", "layer": "<слой>", "reason": "<почему не сделано>"}],
  "report": {
    "outside_changes": ["<путь: что изменено вне целевых файлов>"],
    "tests": "<какие тесты запущены и результат>",
    "questions": ["<допущение или вопрос>"],
    "decisions": ["<принятое решение: имена, поля, SQL>"]
  }
}
```

- Задача-план адресуется парой `plan` + `layer`: студия сама находит узел слоя в
  коде. Если в слое несколько узлов (например io), запись отклоняется с
  перечнем `id` — укажите `id` узла. Задача-узел — `id` или якорь из ТЗ.
  Для ТЗ фронтенда — `id` вида `page:<папка>` и `block:<папка>:<Компонент>`.
- Статус выполнения определяет `studio verify`, а не отчёт: запись для узла,
  которого в коде нет (слой плана не `done`), отклоняется с причиной. Слой
  `test` и узлы вида test описаний не хранят.
- Остальные правила приёма — те же, что для синхронизации (ниже). В метаданные
  пишутся только `description` и `acceptance` отмеченных записей.
- `report` только показывается пользователю в блоке «Отчёт агента»: решения,
  допущения и вопросы в метаданные не попадают. Неизвестные поля `report`
  игнорируются с предупреждением.
- Принимается в окне ТЗ, вкладка «Принять отчёт агента», тем же
  `POST /api/sync/apply` (карта) и `POST /api/frontend/sync/apply` (фронтенд).

### Как агент отдаёт отчёт студии

Агент отправляет итог не в чат, а в студию: `studio_report(summary, part, updates,
not_synced, report)` (`part="frontend"` — для ТЗ фронтенда). `summary` — понятный человеку
текст (что сделано, что проверено, что осталось); он показывается на этапе «Отчёт»
дорожной карты. `updates`, `not_synced`, `report` — тот же JSON, что и раньше, но
необязательный. Ответ сразу показывает, сколько записей изменится и какие отклонены
(поле `rejected` с причиной), так что ошибку можно исправить и отправить заново. Отчёт
попадает в «ждущие решения» (`studio_reports` — статусы `pending`, `accepted`, `rejected`);
описания из `updates` применяет только пользователь в интерфейсе.

## JSON-ответ на промпт синхронизации

Промпт синхронизации описаний (карта и фронтенд) требует от агента один
JSON-блок, а не правку файлов:

```json
{
  "updates": [
    {"id": "<id из таблицы промпта>", "description": "<фактическое описание>",
     "acceptance": ["<проверяемый критерий>"]}
  ],
  "not_synced": [
    {"id": "<id из таблицы промпта>", "reason": "<почему не обновлено>"}
  ]
}
```

Правила приёма (диалог синхронизации → «Принять ответ»):

- JSON ищется в ответе целиком: чистый JSON, блок `json` в тройных кавычках
  или объект внутри текста. Нет объекта с массивом `updates` — ответ
  отклоняется целиком.
- Каждая запись `updates` проверяется отдельно. Отклоняется (с причиной), если:
  нет строкового `id`; `id` не найден среди фактических узлов (плановые узлы
  и правила не синхронизируются); `id` повторяется; `description` — не
  непустая строка; `acceptance` — не массив строк. Лишние поля игнорируются с
  предупреждением.
- Запись «без изменений» (то же описание и критерии) в запись не идёт.
- `not_synced` — справочный список узлов, в которых агент не уверен; он только
  показывается пользователю.
- Пишутся только `description` и `acceptance` отмеченных пользователем записей,
  по кнопке «Применить»; домены, связи, структура JSON и код не меняются.

HTTP: `POST /api/sync/apply` (карта) и `POST /api/frontend/sync/apply`
(фронтенд) с телом `{"json": "<ответ агента>"}` возвращают проверку без записи;
запись — только при `"apply": true` (необязательный `"ids": [...]` ограничивает
набор записываемых узлов).

## Проверка: только факты

По каждой задаче `studio verify` задаёт три вопроса:

1. узлы всех слоёв цепочки появились в коде?
2. связи есть в коде (endpoint → scenario → io → model)?
3. тест найден (если он включён в план)?

Статусы: **выполнено** (все три «да»), **частично** (узел есть, но связи или
теста нет), **не сделано** (узла нет). Никаких «почти» и процентов.

Коды возврата: `0` — все задачи выполнены, `1` — есть «частично» или «не
сделано», `2` — ТЗ не найдено. Отчёт печатает по каждой задаче цепочку
`узел → связи → тест → итог` с путями `path:line`.

## Проверка ТЗ фронтенда

`studio verify --part frontend` (и кнопка «Проверить ТЗ» во вкладке «Фронтенд»)
читает последнее ТЗ фронтенда — по маркеру `studio-front-brief` в
`.studio/agent-brief-frontend.md` — и проверяет задачи по коду `frontend/`:

- плановая страница: есть папка страницы с тем же именем; маршрут совпадает с
  заданным; эндпоинты из `calls` есть в бэкенде;
- плановый блок: компонент с тем же именем используется на странице;
- убрать блок или страницу: их в коде больше нет;
- правило: отмечено «Реализовано» (это решает человек);
- нарушение: сканер больше не видит такую пару «код + файл».

Код возврата 0 — всё выполнено, 1 — нет, 2 — ТЗ не найдено.

## Ограничения

Документ собирается локально и детерминированно: один граф и одни настройки
дают одинаковые байты, кроме строки «Сформировано». Секреты из `.env*` в
документ не попадают.
