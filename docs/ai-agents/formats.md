# Форматы данных цепочки

## Общие правила

Все артефакты цепочки — JSON-файлы в `.studio/chain/`. В студии роли будут писать их только через
MCP-инструменты, а студия — проверять каждую запись по схеме и ссылкам. В прототипе роли пишут файлы сами,
а проверяет команда `studio chain check`.

- **Корень каждого файла:** `{"version": 1, ...}`. При смене схемы растёт `version`, а студия мигрирует файл.
- **Идентификаторы:** `<префикс>.<номер>`, например `need.12`, `req.7`. Идентификаторы не переиспользуются,
  удалённый объект получает `status: "removed"` и остаётся в файле.
- **Ссылки:** только по идентификаторам (`need_ids`, `source_ids`). Ссылка на несуществующий объект — ошибка
  записи.
- **Автор и прогон:** каждый объект несёт `run` (номер прогона из `chain.json`), чтобы было видно, какой прогон
  его добавил.
- **Даты:** ISO 8601 (`2026-11-09T08:30:00+08:00`).

**Цепочка трассировки** — от источника до проверки, каждое звено ссылается на предыдущее:

1. `src` — источник (страница со ссылкой)
2. `fact` — факт из источника
3. `need` — потребность роли
4. `req` — требование
5. `page` / `block` — страница или блок фронтенда
6. `journey` — сквозной путь, по которому идёт тест

## Карта артефактов

| Файл | Шаги | Пишет | Читает |
| --- | --- | --- | --- |
| `chain.json` | все | студия (в прототипе — дирижёр) | все роли (только свой шаг и настройки) |
| `domain.json` | 1 | Исследователь | Исследователь, Продакт, Аналитик |
| `research/run-N-<stream>.json` | 2 | Исследователь (черновик направления) | `studio chain merge-research` |
| `research.json` | 2 | только `studio chain merge-research` | Аналитик, Критик, Решающий |
| `needs.json` | 3 | Аналитик | Продакт, Аналитик, Критик, Решающий |
| `product.json` | 4 | Продакт; `selected` — студия | Аналитик, Ревьюер, Решающий |
| `requirements.json` | 5-7 | Аналитик (требования); Ревьюер (словарь, сущности, сквозные пути) | Критик, Ревьюер, Решающий, Фронтенд-разработчик |
| `remarks.json` | 6-7 | Критик, Ревьюер; статусы — Аналитик | Аналитик, Решающий |
| `decisions.json` | 1, 3, 4, 8 | вы или Решающий | все последующие роли |
| `contract.json` | 9 | Фронтенд-разработчик | Тестировщик, цепочка «Бэкенд» |
| `test-report.json` | 10 | Тестировщик | Фронтенд-разработчик, вы |
| `acceptance.json` | 11 | вы | Фронтенд-разработчик |

## chain.json

Состояние цепочки и настройки шагов; роли его не меняют.

```json
{
  "version": 1,
  "step": 6,
  "status": "running",
  "settings": {
    "1": {"decider": "human"},
    "2": {"repeat": 3, "early_stop_min_new": 5},
    "3": {"decider": "auto"},
    "4": {"repeat": 2, "early_stop_min_new": 1, "decider": "human"},
    "6": {"repeat": 3},
    "7": {"repeat": 2},
    "8": {"decider": "auto"}
  },
  "runs": [
    {"run": 14, "step": 6, "role": "critic", "round": 2,
     "started_at": "2026-11-09T08:30:00+08:00", "finished_at": null,
     "added": {}, "result": null}
  ]
}
```

- `status`: `running` (роль работает), `waiting_human` (ваш ход), `done`.
- `repeat` — N прогонов или раундов; `early_stop_min_new` — сколько новых объектов должен добавить прогон,
  чтобы цепочка шла дальше.
- `decider`: `human` или `auto` (Решающий). Шаг 11 этой настройки не имеет.
- `added` — сколько объектов каждого типа добавил прогон, например `{"fact": 12, "src": 7}`.

## domain.json

Рамка поиска из сырой идеи: область и роли, без формулировки продукта.

```json
{
  "version": 1,
  "raw_idea": "сайт для автосервиса",
  "domain": "Небольшие автосервисы, их клиенты и мастера",
  "roles": [
    {"id": "role.1", "name": "Клиент", "description": "владелец авто, обращается за ремонтом", "run": 1},
    {"id": "role.2", "name": "Мастер", "description": "выполняет работы по заказ-наряду", "run": 1},
    {"id": "role.3", "name": "Администратор", "description": "принимает заявки, ведёт расписание", "run": 1}
  ],
  "search_directions": [
    "как клиенты выбирают автосервис и записываются",
    "на что жалуются клиенты в отзывах",
    "программы учёта для автосервисов"
  ]
}
```

Роли из этого файла — единственный список ролей цепочки: другие файлы ссылаются на них по `role.N`.

## research.json

Факты исследования со ссылками. Три исследователя пишут черновики своих направлений
(`research/run-N-needs.json`, `-competitors.json`, `-norms.json`) с локальными идентификаторами с 1, а команда
`studio chain merge-research N` вливает их в `research.json`, перенумеровывает и не дублирует источники с тем же
url.

```json
{
  "version": 1,
  "sources": [
    {"id": "src.1", "url": "https://example.com/reviews/autoservice", "title": "Отзывы об автосервисах города",
     "kind": "review", "accessed": "2026-11-09", "run": 2}
  ],
  "facts": [
    {"id": "fact.1", "stream": "needs", "kind": "pain", "role_id": "role.1",
     "text": "Клиенты жалуются, что не могут дозвониться для записи",
     "evidence": "встречается в 14 из 60 отзывов", "source_ids": ["src.1"], "run": 2},
    {"id": "fact.2", "stream": "norms", "kind": "norm", "role_id": null,
     "text": "Сбор персональных данных клиента требует согласия на обработку",
     "evidence": "", "source_ids": ["src.4"], "run": 2}
  ],
  "competitors": [
    {"id": "comp.1", "name": "Конкурент А", "url": "https://example.com/competitor-a",
     "segment": "запись и учёт для автосервисов", "source_ids": ["src.2"], "run": 2,
     "features": [
       {"id": "feat.1", "name": "Онлайн-запись", "description": "виджет записи на сайте", "source_ids": ["src.2"]}
     ]}
  ]
}
```

- `stream`: `needs` (потребности и боли), `competitors`, `norms`.
- `kind` факта: `pain`, `need`, `norm`, `observation`.
- `source.kind`: `review`, `forum`, `article`, `competitor_site`, `law`, `standard`.
- `evidence` — чем подкреплён факт (частота, цитата до 15 слов, номер статьи закона); может быть пустым.
- Факт или функцию конкурента без `source_ids` проверка не принимает.

## needs.json

Карта потребностей: каждая потребность принадлежит роли, опирается на факты и оценена по трём шкалам.

```json
{
  "version": 1,
  "needs": [
    {"id": "need.1", "role_id": "role.1",
     "statement": "Записаться на ремонт без звонка, в том числе в нерабочее время",
     "fact_ids": ["fact.1", "fact.7"],
     "frequency": "high", "severity": "high",
     "coverage": "partial", "covered_by": ["comp.1", "comp.3"],
     "required_by_norm": false,
     "rank": 1, "status": "active", "run": 3}
  ]
}
```

- `frequency` и `severity`: `high`, `medium`, `low` — насколько часто встречается и насколько больно.
- `coverage`: `none`, `partial`, `full` — насколько хорошо потребность закрывают конкуренты; `covered_by` — кто.
- `required_by_norm`: `true`, если потребность следует из нормы (`fact.kind = norm`).
- `rank` — место в общем списке; меньше значит важнее.

## product.json

Варианты формулировки продукта и выбранный вариант; новые прогоны добавляют варианты, старые не удаляются.

```json
{
  "version": 1,
  "variants": [
    {"id": "var.1", "run": 4,
     "statement": "Сервис записи и ведения заказов для небольших автосервисов: клиент записывается сам и видит статус ремонта",
     "role_ids": ["role.1", "role.3"],
     "need_ids": ["need.1", "need.2", "need.5"],
     "differentiation": "статус ремонта онлайн, которого нет у 5 из 7 конкурентов",
     "out_of_scope": ["склад запчастей", "бухгалтерия"],
     "differs_from_raw_idea": "сырая идея говорила о сайте-визитке; потребности указывают на запись и статус"}
  ],
  "selected": "var.1",
  "decision_id": "dec.3"
}
```

- `need_ids` выбранного варианта — список потребностей, которые продукт обязан закрыть. Шаги 5-7 проверяют
  покрытие именно по нему.
- `out_of_scope` — явные границы; Критик отклоняет требования, которые в них попадают.
- `differs_from_raw_idea` объясняет, чем вариант отличается от сырой идеи, или пустая строка, если не
  отличается.

## requirements.json

Центральный файл цепочки: требования, а также словарь, сущности и сквозные пути, которые держат продукт
согласованным.

```json
{
  "version": 1,
  "round": 2,
  "glossary": [
    {"id": "term.1", "term": "Запись", "definition": "бронь времени клиента на услугу",
     "forbidden_synonyms": ["бронь", "заявка"]}
  ],
  "entities": [
    {"id": "ent.1", "name": "Запись", "term_id": "term.1",
     "states": ["new", "confirmed", "done", "cancelled"]}
  ],
  "areas": [
    {"id": "area.1", "name": "Запись на услуги", "domain": "booking"}
  ],
  "items": [
    {"id": "req.1", "area_id": "area.1", "type": "mandatory",
     "title": "Онлайн-запись на свободное время",
     "description": "клиент выбирает услугу и свободный слот и создаёт запись",
     "role_ids": ["role.1"], "need_ids": ["need.1"], "entity_ids": ["ent.1"],
     "benefit": "клиент не теряется, если не дозвонился; сервис получает заявки круглосуточно",
     "justification": [
       {"basis": "competitors", "text": "есть у 6 из 7 конкурентов", "competitor_ids": ["comp.1"], "source_ids": ["src.2"]},
       {"basis": "pain", "text": "частая жалоба в отзывах", "source_ids": ["src.1"]}
     ],
     "acceptance": ["занятый слот выбрать нельзя", "после записи клиент видит её в своём списке"],
     "no_ui": false, "status": "active", "run": 5,
     "history": [{"round": 1, "by": "analyst", "change": "уточнено описание", "remark_id": "rem.4"}]}
  ],
  "journeys": [
    {"id": "journey.1", "role_id": "role.1", "name": "Записаться и прийти на ремонт",
     "steps": [
       {"n": 1, "action": "выбрать услугу и время", "req_id": "req.1"},
       {"n": 2, "action": "получить подтверждение", "req_id": "req.4"}
     ]}
  ]
}
```

- `type`: `mandatory` (обязательно) или `proposed` (предлагаем).
- `basis` обоснования: `competitors`, `pain`, `norm`, `logic`. Для `logic` источник не нужен, для остальных
  обязателен.
- `no_ui: true` — требование без интерфейса; оно идёт в цепочку «Бэкенд», а не на шаг 9.
- `areas[].domain` — латинское имя области; оно же станет `domain` в карточках студии.
- `glossary`, `entities`, `journeys` ведёт Ревьюер согласованности; Аналитик может предложить изменение только
  через замечание.

## remarks.json и decisions.json

Замечания критика и ревьюера живут отдельно от требований, а каждое решение — ваше или Решающего — попадает в
журнал с обоснованием.

```json
{
  "version": 1,
  "remarks": [
    {"id": "rem.4", "step": 7, "round": 1, "by": "reviewer",
     "check": "glossary", "severity": "blocking",
     "target_ids": ["req.1", "req.9"],
     "text": "в req.9 запись названа «заявкой»",
     "fix_hint": "заменить на термин term.1",
     "status": "fixed", "resolution": "req.9 переименовано в раунде 2"}
  ]
}
```

- `check`: на шаге 6 — `coverage`, `source`, `duplicate`, `scope`, `benefit`; на шаге 7 — `glossary`, `roles`,
  `journey`, `entity`, `pattern`, `navigation`, `contradiction`.
- `severity`: `blocking` или `minor`. Раунды идут, пока есть открытые `blocking`.
- `status`: `open`, `fixed`, `rejected` (Аналитик не согласен — с объяснением в `resolution`).

```json
{
  "version": 1,
  "decisions": [
    {"id": "dec.11", "step": 8, "target_id": "req.12", "decision": "reject",
     "by": "decider", "contested": true,
     "reason": "дублирует req.3 и выходит за границу «бухгалтерия»",
     "pros": ["закрывает need.6"], "cons": ["вне границ продукта", "нет источника"],
     "extra_check": "повторный поиск: у 1 из 7 конкурентов",
     "overridden_by": null, "at": "2026-11-09T09:10:00+08:00"}
  ]
}
```

- `decision`: `accept`, `reject` (пункт) или `select` (вариант на шаге 4, подтверждение на шаге 1 с
  `target_id: "domain"`).
- `by`: `human` или `decider`. Для `contested: true` поля `pros`, `cons`, `extra_check` обязательны.
- Если вы переиграли решение, создаётся новая запись, а у старой заполняется `overridden_by`.

## contract.json

Контракт фронтенда: страницы и блоки в нынешнем формате студии плюс ссылки на требования и формы данных
каждого вызова; после шага 11 он замораживается и передаётся в цепочку «Бэкенд».

```json
{
  "version": 1,
  "status": "draft",
  "frozen_at": null,
  "pages": [
    {"name": "booking", "title": "Запись на ремонт", "route": "/booking", "domain": "booking",
     "description": "клиент выбирает услугу и время", "acceptance": ["занятый слот выбрать нельзя"],
     "role_ids": ["role.1"], "req_ids": ["req.1"], "calls": [],
     "blocks": [
       {"name": "SlotPicker", "description": "свободные слоты на неделю",
        "acceptance": ["пока данные грузятся — заглушка"],
        "req_ids": ["req.1"], "calls": ["GET /booking/slots"]}
     ]}
  ],
  "endpoints": [
    {"call": "GET /booking/slots", "entity_ids": ["ent.1"],
     "request": {"query": [{"name": "service_id", "type": "int", "required": true}]},
     "response": {"type": "list", "of": [
       {"name": "start", "type": "datetime", "required": true},
       {"name": "free", "type": "bool", "required": true}]},
     "errors": [{"status": 422, "when": "service_id не передан"}],
     "mock": "frontend/src/mocks/booking-slots.json"}
  ]
}
```

- Поля страницы и блока совпадают с нынешним форматом `pages` студии (`name` в kebab-case, блок в PascalCase,
  `calls` строками «METHOD /path» без префикса API); добавлены `role_ids` и `req_ids`.
- Типы полей: `string`, `int`, `number`, `bool`, `date`, `datetime`, `money`, `enum` (с `values`), `ref`
  (с `entity_id`), `object` (с `fields`), `list` (с `of`).
- `mock` — файл фикстуры, по которому работает слой API фронтенда до появления бэкенда.
- `status`: `draft` → `frozen` после «Принять» на шаге 11. Правка замороженного контракта создаёт новую версию и
  разницу для бэкенда.

## test-report.json и acceptance.json

Оба теста идут по сквозным путям из `requirements.json`, поэтому результаты агента и ваши сравниваются путь за
путём.

```json
{
  "version": 1,
  "runs": [
    {"run": 22, "iteration": 1,
     "journeys": [
       {"journey_id": "journey.1", "status": "failed",
        "steps": [
          {"n": 1, "status": "passed"},
          {"n": 2, "status": "failed", "page": "booking", "block": "SlotPicker",
           "message": "после записи нет перехода к подтверждению"}
        ]}
     ],
     "unit": {"tool": "vitest", "passed": 41, "failed": 2},
     "issues": [
       {"id": "iss.1", "journey_id": "journey.1", "step": 2, "severity": "blocking",
        "text": "тупик после создания записи", "req_ids": ["req.4"]}
     ]}
  ]
}
```

- Статус шага пути: `passed`, `failed`, `blocked` (не дошли из-за предыдущей ошибки).
- Любой `blocking` в `issues` возвращает цепочку на шаг 9.

```json
{
  "version": 1,
  "rounds": [
    {"n": 1, "verdict": "return", "at": "2026-11-09T12:00:00+08:00",
     "remarks": [
       {"page": "booking", "block": "SlotPicker", "journey_id": "journey.1",
        "text": "слоты мелкие, на телефоне не попасть пальцем"}
     ]}
  ]
}
```

- `verdict`: `return` (замечания уходят на шаг 9) или `accept` (контракт замораживается).
- Замечание можно привязать к странице, блоку или пути; ни одна привязка не обязательна.

## Механические проверки

Эти проверки выполняет код, без LLM (`studio chain check`, модуль `studio/productchain/check.py`): ошибка
отклоняет запись роли, блокирующее замечание не пускает цепочку дальше, предупреждение показывается вам и
ревьюеру. Код выхода: 0 — чисто, 1 — есть ошибки, 2 — есть только блокирующие замечания.

| Проверка | Когда | Уровень |
| --- | --- | --- |
| Каждая ссылка (`*_id`, `*_ids`, `selected`, `overridden_by`) указывает на существующий объект; нет дублей идентификаторов | любая запись | ошибка |
| У факта, конкурента и функции конкурента есть `source_ids`; url источника начинается с http(s) | шаг 2 | ошибка |
| У потребности есть хотя бы один `fact_id`, оценки из допустимых значений | шаг 3 | ошибка |
| У требования есть `need_ids`, польза и обоснование; у обоснования с `basis` кроме `logic` есть `source_ids` | шаги 5-7 | ошибка |
| Каждая потребность из `need_ids` выбранного варианта закрыта хотя бы одним активным требованием | шаги 5-8 | блокирующее замечание |
| Названия в требованиях не содержат `forbidden_synonyms` словаря (в любом падеже) | шаги 5-7 | блокирующее замечание |
| Каждый шаг сквозного пути ссылается на активное требование | шаги 7-8 | блокирующее замечание |
| Открытые блокирующие замечания в `remarks.json` | шаги 6-7 | блокирующее замечание |
| У спорного решения есть плюсы, минусы и перепроверка | шаги 1, 3, 4, 8 | ошибка |
| У каждой роли выбранного варианта есть хотя бы один сквозной путь | шаги 7-8 | предупреждение |
| Каждое выбранное требование без `no_ui` есть в какой-то странице или блоке контракта | шаг 9 | ошибка |
| Каждый `calls` страницы и блока есть в `endpoints`, у каждого эндпоинта есть `mock` | шаг 9 | ошибка |
| На каждую страницу ведёт хотя бы один путь или ссылка навигации | шаг 9 | предупреждение (пока не реализовано) |
| Замороженный контракт не меняется без новой версии | после шага 11 | ошибка (пока не реализовано) |
