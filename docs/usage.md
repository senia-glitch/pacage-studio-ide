# Как пользоваться студией

## Быстрый цикл

```powershell
studio doctor                  # проверить источники и окружение
studio                         # автоскан + интерфейс, открывает браузер
studio dev                     # то же явно: --host, --port, --no-open, --poll, --verbose
studio scan [--json]           # только скан → .studio/graph.json
studio list [--json]           # сценарии в терминале
studio brief [--stdout] [--plan SLUG] [--only ANCHOR] [--scenario NAME] [--section NAME]
studio verify [BRIEF] [--part backend|frontend]   # проверить выполнение ТЗ (по структуре кода)
studio test [--json]           # прогнать тесты проекта (.studio/tests.json) и привязать итог к планам
studio migrate [--apply]       # убрать заглушки старой модели из metadata.json (по умолчанию — показать)
studio report [--part backend|frontend] [--section NAME ...] [--stdout | --json]
studio skill [--target stdout|claude|agents|all]   # руководство для AI-агента
studio mcp                     # MCP-сервер для AI-агента (stdio), см. mcp.md
studio chain install [--dest DIR] [--force]   # роли и скиллы цепочки в OpenCode
studio chain check [--json]    # проверки артефактов .studio/chain (merge-research N, summary)
studio install-full            # fastbase[full] в текущий venv
studio help                    # все команды
studio --version               # версия пакета
```

Про ТЗ для AI-агента — в [agent-brief.md](agent-brief.md).

## Рабочие области

### Карта проекта

Карта показывает фактические узлы проекта и плановые узлы в одной структуре.
Переключатель **«Факт»** приглушает плановые узлы и плановые пометки изменений;
**«План»** приглушает фактические узлы. HTTP-методы и домены отображаются как
группы. Домены можно добавить в план или предложить переименовать; до реализации
код и фактические данные не меняются.

Нажмите на карточку, чтобы открыть её свойства в правой панели. У фактического
узла можно записать заметку о будущей правке и критерии приёмки. У планового
узла можно менять название, описание и критерии. Наведите курсор на карточку и
нажмите **＋**, чтобы добавить потомка. Типы узлов зависят от типа родителя;
плановую ветку можно удалить целиком, фактический код при этом сохраняется.
Правую панель можно скрыть или изменить её ширину перетаскиванием разделителя.
Карта автоматически располагает карточки без наложений.
Перетаскивайте карточку за любую свободную область: её потомки двигаются
вместе, а у соседних карточек ветка скользит вдоль края без пересечения.

У каждого эндпойнта своя компактная ветка, которая раскрывается сверху вниз.
Если несколько эндпойнтов используют один узел, карта показывает его копию в
каждой соответствующей ветке. Это один узел в плане: выбор любой копии
подсвечивает остальные, а редактирование и добавление потомков применяются ко
всем отображениям.

Поиск (`/`) фильтрует карту по имени, URL, домену и описанию. Используйте
**«Обновить код»**, чтобы перечитать проект после изменений в IDE. Структуру
фактических узлов меняйте в IDE; карта сканирует код и хранит планы отдельно в
`.studio/metadata.json`.

### Генератор идей

Создайте узел идеи и опишите задачу. Кнопка **«Собрать промпт»** готовит
промпт с контекстом проекта; `studio` не вызывает LLM. Скопируйте промпт,
обсудите его с LLM и вставьте ответ JSON в корневой узел. Общий поиск в шапке
фильтрует доску по названию идеи, описанию, названию сценария и домену. Кнопка
**«Разобрать сценарии»** создаст карточки-сценарии в связанной ветке.

Если задача затрагивает интерфейс, промпт просит у LLM ещё и ключ `pages` —
страницы и блоки фронтенда (папка, маршрут, роль, вызываемые эндпоинты).
**«Разобрать ответ»** принимает ответ целиком: JSON можно оставить внутри
```-блока и среди текста. Сценарии бэкенда и страницы фронтенда появляются двумя
ветками (переключатель **«Бэкенд | Фронтенд»** над веткой); **«Во фронтенд ↗»**
создаёт плановую страницу и блоки во вкладке «Фронтенд» (повторная передача
обновляет те же узлы) и сообщает, каких эндпоинтов ещё нет в бэкенде.

Карточки можно править и явно передавать сценарии в план общей карты. Удаление
карточки удаляет её сценарий из JSON идеи. Доска идей (идеи, промпты и ветки)
хранится в проекте — `.studio/ideas.json` — и переносится вместе с ним.
**«Экспорт»** и **«Импорт»** делают резервную копию доски и восстанавливают её.

### Отчёт по проекту

Кнопка **«Отчёт»** на верхней панели карты и команда `studio report` собирают
отчёт о том, что уже есть в проекте (а не задачи на будущее — это ТЗ). Разделы
включаются флажками, порядок у них фиксированный:

- **Сводка** — число эндпоинтов, сценариев, io, моделей и тестов (с плановыми),
  домены и планы;
- **Структура** — домен → HTTP-метод → эндпоинт → сценарий → io → модель, тесты;
- **Покрытие** — сколько узлов с описанием, критериями и тестом, и список узлов
  без описания;
- **Планы** — статус каждого плана и его слоёв;
- **Модели** — таблицы, число полей и сценарии, которые в них пишут;
- **Диагностика** — предупреждения скана и жёлтые пометки.

В окне отчёта текст можно править (копирование и скачивание берут ваш
вариант), «Скачать .json» отдаёт те же сведения структурно. Файл —
`.studio/report.md`. Команда: `studio report` пишет файл, `--stdout` печатает
markdown, `--json` — `{path, markdown, data}`, `--section summary --section
models` выбирает разделы, `--part frontend` — отчёт по `frontend/`
(`.studio/frontend-report.md`). Неизвестный раздел — ошибка (код возврата 2).

### Фронтенд

Вкладка «Фронтенд» читает `frontend/` проекта (Vue 3 + Pinia + Router + Vite):
карта страниц и блоков по слоям `ui/…` → `logic/…`, правила DAG и UI-стандарта,
нарушения с `файл:строка`. Описания, критерии, домены (роли) и правила страниц
и блоков хранятся в `.studio/frontend.json`; код `frontend/` студия не меняет.

- **⇄ ТЗ…** — ТЗ для AI-агента: область (выбранный узел и потомки / весь
  фронтенд / только нарушения) и разделы «Область работ», «Связи с бэкендом»,
  «Нарушения», «Проверка» выбираются в окне; текст можно править прямо там — «Скопировать»
  и «Скачать» берут ваш вариант, файл `.studio/agent-brief-frontend.md`
  хранит исходный.
- **Проверить ТЗ** — сверяет последнее ТЗ фронтенда с кодом `frontend/`:
  плановые страницы и блоки появились, убираемые — исчезли, объявленные вызовы
  эндпоинтов находят эндпоинт в бэкенде. Правила код проверить не может — их
  отмечаете вы («Реализовано»). То же из терминала: `studio verify --part frontend`.
- **Отчёт** — инвентаризация фронтенда; разделы (стек и сводка, замечания
  проекта, структура, покрытие правил, нарушения, связи импортов) включаются
  флажками; «Скачать .json» отдаёт те же сведения структурно.
- **⇄ Синхр. описаний** — см. следующий раздел.
- **Связи с бэкендом.** В свойствах страницы и блока — поле «Вызывает эндпоинты
  бэкенда» (по одному `МЕТОД /путь` на строку, префикс API можно не писать).
  Студия сверяет вызовы с эндпоинтами бэкенда, фактическими и плановыми, и
  показывает ✓ или ✗; недостающие эндпоинты попадают в ТЗ (раздел «Связи с
  бэкендом»). Сканер кода вызовы не ищет: связи объявляете вы или агент в режиме
  планирования.

### Синхронизация описаний с кодом

Кнопка «⇄ Синхр. описаний» на верхней панели карты и на вкладке «Фронтенд»
открывают диалог из двух шагов:

1. **Промпт.** Выберите область (весь проект / домен / страница / узлы без
   описания), скопируйте промпт и отдайте AI-агенту с доступом к папке проекта.
   Агент читает код и отвечает одним JSON-блоком; файлы он не правит.
2. **Принять ответ.** Вставьте ответ агента (можно целиком, вместе с текстом
   вокруг блока `json`) и нажмите «Проверить»: студия покажет по каждой записи,
   что изменится, а что отклонено и почему. «Применить выбранные» записывает в
   метаданные только отмеченные записи — и только `description` и `acceptance`.

Формат ответа — в [agent-brief.md](agent-brief.md).

После «Применить» рядом с итогом появляется **«↩ Отменить применение»**: он
возвращает прежние описания и критерии. Узел, который вы успели изменить уже
после применения, отмена не трогает — студия пишет, сколько узлов пропущено.

То же окно «Принять…» есть у ТЗ: итоговый отчёт агента по ТЗ — строгий JSON.
В окне ТЗ откройте вкладку «Принять отчёт агента», вставьте ответ — студия
сверит записи с кодом, покажет отличия и блок «Отчёт агента» (тесты, решения,
вопросы), а описания и критерии реализованных узлов запишет только по «Применить».

### Дорожная карта и работа с AI-агентом

Полоса под шапкой показывает, на каком этапе цепочка; справа — подсказка, главная кнопка
этапа и индикатор «● агент» (зелёный — агент недавно обращался к студии). Окна открываются
сами при входе на этап (один раз; потом — кнопкой этапа). «⟲ Заново» сбрасывает этап, а не
карту и не код.

0. **Подключение (один раз).** `claude mcp add pacage-studio -- studio mcp` и
   `studio skill --target all`. Дальше запустите агента в папке проекта и попросите работать со
   студией: он вызовет `studio_connect` и `studio_workflow`. Токен копировать не нужно —
   студия пишет адрес и токены в `.studio/server.json` (файл игнорируется git и удаляется при
   остановке студии). Кнопка **«AI-агент»** осталась запасным способом (строка с адресом и токеном).
1. **Синхронизация.** Этап отмечается выполненным, как только агент обратится к студии.
2. **Режим.** Окно «С чего начнём?». *Планирование* — агент придумывает идеи (в поле можно
   описать задачу); *реализация* — сразу к выбору уже запланированных задач.
3. **Идеи.** Агент присылает идеи (`studio_idea_add`): сценарии и страницы приходят уже
   разобранными, со slug (латиница) и описанием. Ошибки (плохой slug, занятое имя, нет
   описания) агент получает сразу и исправляет сам.
4. **Валидация.** Полноэкранное окно с карточками. Потяните карточку вверх — принять, вниз —
   отклонить; то же кнопками и клавишами ↑ ↓, **Z** вернёт прошлую. Решения сохраняются сразу
   (`.studio/ideas.json`), окно можно закрыть и вернуться.
5. **Перенос.** «Принять все запланированные идеи и их сценарии?» «Да» создаёт на карте
   планы (имена по slug: функция `list_lessons`, класс `ListLessonsScenario`, целевые файлы)
   и плановые страницы фронтенда; «Нет» возвращает к карточкам. Ошибки по отдельным карточкам
   показываются в окне, остальное переносится.
6. **Выбор.** Чекбоксы по сценариям, плановым узлам и страницам (без описания — недоступны).
   «Отдать агенту» сохраняет ТЗ только по отмеченному.
7. **Реализация.** Агент берёт ТЗ (`studio_brief`), пишет код, проверяет (`studio_verify`),
   отправляет отчёт. На полосе — «выполнено x из y» по коду. Если отчёт не нужен, работу можно
   принять вручную.
8. **Отчёт.** Текст агента, проверка студии по коду и (если агент предложил) обновления описаний —
   они записываются только по вашему «Применить». «Всё хорошо — начать заново» завершает цикл;
   «Вернуть к выбору задач» отдаёт агенту ещё работу.

**Независимая проверка тестами.** `studio_verify` смотрит на структуру кода, а поведение доказывают
тесты. Поэтому на этапе «Отчёт» есть блок «Тесты проекта» с кнопкой «Запустить тесты проекта»
(и галочка «Запускать тесты, когда агент прислал отчёт» в «⚙ Автозапуск»; выключена по умолчанию).
Студия сама запускает `pytest` (в окружении проекта: `.venv`/`venv`, иначе — студии) и, если в
`frontend/package.json` есть скрипт `test`, тесты фронтенда (`npm test`, отчёт Vitest в JUnit). Команды
и предел времени — `.studio/tests.json` (`command`, `frontend_command`; пустой список отключает
фронтенд). Студия показывает, сколько прошло по каждой части, что упало и у каких планов; то же из терминала — `studio test` (код выхода 1 при
падениях). Агент читает итог инструментом `studio_tests`, но запустить прогон не может.

**Автозапуск агента.** Кнопка **«⚙ Автозапуск»** на полосе открывает настройку. Если включить
автозапуск, студия сама запускает команду агента в папке проекта, когда цепочка входит на этап
«Идеи агента» или «Реализация» (после выбора режима «планирование» и после «Отдать агенту»);
агент делает этап и завершается — вручную держать его в ожидании не нужно, а простой не тратит
лимиты. Команда — список аргументов, по одному на строку; `{prompt}` заменяется текстом запроса.
По умолчанию — `claude -p …` (или `opencode run …`, если выбран OpenCode) с правом править файлы,
запускать `python`, `pytest`, `npm` и инструменты студии; поменяйте под своего агента. Агент и его
модель выбираются отдельно для плана и для реализации на странице «Настройки агента»
(`roles.plan` и `roles.implement` с `agent`, `model`, `variant` в `.studio/runner.json`; команды запуска
хранятся по агентам в `commands`); модели OpenCode — из `opencode models --verbose`, то есть только из ваших
подписок (платные по токенам скрыты, пока не включён переключатель), модель Claude Code — `opus`,
`sonnet`, `haiku` или полное имя (пусто — по умолчанию). Уровень усилий (`variant`): у Claude Code
`low`, `medium`, `high`, `xhigh`, `max` (`--effort`), у OpenCode — один из вариантов выбранной модели
(`--variant`); пусто — по умолчанию. Вывод процесса — `.studio/runner.log`. Если
агент завершился, а этап не продвинулся (или упал), на полосе появится причина и кнопка
«↻ Запустить агента». «⟲ Заново» останавливает запущенного агента. Включает автозапуск только
человек в интерфейсе; агенту эти маршруты закрыты. Выключено по умолчанию.

### Автоматический ход цикла

Настройки задаются на шаге «Цель» перед «Начать» (и действуют на весь цикл, пока агент подключён):

- **Итераций идей (1–5).** Агент запускается на «Идеи» несколько раз подряд. В запросе итерации *k*
  студия передаёт список уже существующих карточек (название, маршрут, решение): агент должен
  углубить декомпозицию (разбить крупные сценарии, добавить ошибки, права, граничные случаи,
  страницы) и не повторять ни принятые, ни отклонённые карточки. Если итерация не добавила новых
  карточек, оставшиеся итерации не запускаются. Валидирует человек один раз, после последней.
- **Агент сам принимает и отклоняет карточки.** После каждой итерации отдельный запуск роли
  «Контроль» решает по каждой карточке (`studio_cards_decide`, с короткой причиной): следующая
  итерация строится на принятых. После последней студия сама переносит принятое на карту, отмечает
  все перенесённые задачи и запускает реализацию. Остаётся «Приёмка». Решения человека агент не
  перезаписывает. Если контролёр оставил карточки без решения, цепочка останавливается с причиной
  в окне агента («Повторить» запускает его снова).
- **Проверять каждый сценарий после реализации** и **писать усиленные тесты для каждого сценария.**
  Реализация идёт по сценариям (план бэкенда, узел, страница фронтенда), по одному за запрос:
  реализация → проверка (контролёр читает ТЗ и критерии, смотрит код и тесты, итог через
  `studio_check_result(ok, remarks)`) → при замечаниях реализующий агент исправляет их (до 2 раз) и
  проверка идёт снова → тесты (контролёр пишет и запускает тесты на критерии, ошибки и граничные
  случаи, дефекты реализации только описывает) → следующий сценарий. Замечания, оставшиеся после двух
  исправлений, не останавливают цикл, а попадают в итоговый отчёт. Агент присылает отчёт отдельным
  последним запросом. После каждого запроса студия делает git-чекпоинт.

Контролёр — третья роль на странице «Настройки агента» («Контроль», `roles.check` в
`.studio/runner.json`): свой агент, модель и уровень усилий; пока не выбрано, он повторяет
«Реализацию». Он запускается без прежней сессии: независимый взгляд на чужую работу, а сессия
реализующего агента не затрагивается. Окно агента показывает «Итерация 2 из 3», «Сценарий 3 из 8:
проверка» и список сценариев с отметками (✓ сделан, ⚠ остались замечания, ▶ текущий). Маршруты
`/api/control/*` принимаются только во время запуска соответствующего контролёра. Каждый включённый
шаг — отдельные запуски агента и расход подписки. Выключено по умолчанию: без настроек цепочка идёт
как раньше, одним запросом на этап.

### Серверы проекта

Блок «Проект» в окне агента запускает серверы самого проекта (не студии): «▶ Запустить проект» — бэкенд, а
после того как он ответил, фронтенд; у каждого сервера есть своя кнопка ▶/■. Команды по умолчанию:
бэкенд — `python -m uvicorn app.main:app --reload --host 127.0.0.1 --port {port}` (без `app/main.py` —
`main:app`) из окружения проекта `.venv`; фронтенд — скрипт `dev` из `frontend/package.json`
(`npm run dev -- --port {port} --strictPort`). Запуск фронтенда при остановленном бэкенде поднимает оба.

- **Порт.** Предпочтительный — 8000 и 5173 (в настройках можно задать свой). Если он занят, берётся
  ближайший свободный из следующих 50, и в блоке появляется пометка. Фронтенд получает адрес бэкенда
  в `STUDIO_BACKEND_URL` и `STUDIO_BACKEND_PORT`; если бэкенд ушёл с порта 8000, добавляются
  `BACKEND_URL` и `VITE_BACKEND_URL`. Если прокси фронтенда зашит на 8000, поправьте `vite.config.js`.
- **Ссылка.** Берётся из вывода сервера (`Local: http://localhost:5173/`) и показывается, только когда
  порт отвечает. При сбое видны код выхода и хвост вывода (полный — `.studio/devserver-<имя>.log`);
  нет `frontend/node_modules` — подсказка выполнить `npm install`.
- **Свои команды.** «Настройки агента» → «Серверы проекта» (`.studio/servers.json`: `command` — по
  аргументу на строку, `{port}` заменяется портом, и `port`). Пусто — автоопределение.
- **Остановка.** Серверы завершаются вместе с деревом процессов (npm, node, uvicorn) при «■», при «Остановить
  всё» и при закрытии студии. Запускает их только человек: маршруты `/api/devservers*` закрыты для агента.

Агент работает со студией только через MCP-сервер `studio mcp` (входит в пакет),
инструменты и порядок — в [mcp.md](mcp.md) и [agent-workflow.md](agent-workflow.md); руководство
ставит `studio skill --target claude|agents|all` (без флагов печатает текст).

Права агента зависят от этапа: идеи он пишет только на этапах «Идеи агента» и «Валидация»,
отчёт — только на «Реализации» и «Отчёте»; запись вне этапа студия отклоняет
(`stage_forbidden`). Применять ответы (`apply`), собирать ТЗ и решать по карточкам может
только человек.

Вкладки «Фронтенд» и «Идеи» обновляются сами, пока агент работает; если вы в этот момент вводите
текст, перерисовка ждёт, пока вы закончите. Доска идей хранит `revision`: если вы и агент
правите её одновременно, устаревшая запись отклоняется, а интерфейс загружает актуальную версию.

## Цепочка «Продукт → Фронтенд» (прототип)

Новая цепочка ведёт от сырой идеи через анализ предметной области, конкурентов и норм к обоснованным
требованиям. Пока она работает как прототип в OpenCode (шаги 1-8): `studio chain install` ставит агентов и
скиллы в `.opencode/` проекта (`--dest "$HOME\.config\opencode"` — глобально для всех папок), затем в `opencode` выберите агента
`chain` и напишите идею. Артефакты лежат в `.studio/chain/`, их проверяет `studio chain check` (код выхода 0 —
чисто, 1 — ошибки, 2 — блокирующие замечания); `studio chain merge-research N` вливает черновики исследования,
`studio chain summary` показывает объём. Подробно — [ai-agents/README.md](ai-agents/README.md).

## Страницы фронтенда в идеях

Идея агента может содержать новую страницу (`name`, `route`, `blocks`) или **блоки на
существующей странице** (`extends="home"` и `blocks`): при переносе плановые блоки ложатся
на эту страницу, в «Выборе задач» она подписана «новые блоки: …», а в ТЗ они становятся
задачами. Поля самой страницы в `extends`-карточке не применяются. Пока по идее нет
принятых карточек, агент может отозвать её (`studio_idea_withdraw`); о похожей идее студия
предупреждает.

## Вызовы эндпоинтов и контракт в ТЗ фронтенда

У существующих страниц и блоков студия по тексту кода находит вызовы эндпоинтов (через цепочку
блок → composable → действие → api; для composable учитываются только используемые поля) и
показывает их как «найдено в коде» отдельно от объявленных `calls`. В ТЗ фронтенда у каждого
объявленного вызова, чей эндпоинт уже есть в бэкенде, указан контракт: параметры запроса и тело
с полями модели, `response_model`, код ответа и ключи словаря, который возвращает сценарий.
Это подсказка по тексту, а не гарантия: динамические пути и ответы студия не определит.

## ТЗ для агента: что в нём подобрано

Образцы кода и «что переиспользовать» студия подбирает по смыслу: общие слова имён и путей,
тот же HTTP-метод, домен; служебные узлы (`admin`, `auth`) не берутся, если задача не про них.
Если путь плана окажется позади (или перед) параметрического маршрута, в задаче будет
«⚠ Порядок маршрутов» с двумя рабочими способами. Агенту ТЗ отдаётся по частям; пустые разделы
в оглавлении помечены `empty`, формат якорей `metadata.json` в ТЗ для агента не входит.

`studio_doctor` различает новые и давние предупреждения: на момент «Отдать агенту» студия
запоминает состояние (`.studio/diag-baseline.json`), `ok_for_changes` говорит, нет ли новых
проблем; чужие давние исправлять агент не обязан.

## Старые проекты: `studio migrate`

В проектах, начатых до дорожной карты, в `.studio/metadata.json` остаются записи-заглушки:
слоёв уже реализованных планов и `studio:…`, для которых в коде есть узел с тем же якорем.
`studio migrate` показывает, что можно убрать; `studio migrate --apply` убирает (копия —
`metadata.json.pre-migrate.bak`). Сами планы, описания и код не трогаются.

## Метаданные

Описания, критерии, домены, дополнительные связи и планируемые узлы хранятся
только в `.studio/metadata.json`. Формат — в
[metadata-format.md](metadata-format.md).

## Сохранение состояния

Раскладка, зум, выбранная вкладка и узел, ширина правой панели и переключатели
карты переживают F5: состояние интерфейса лежит в localStorage браузера.
Доска идей — не интерфейсное состояние, она лежит в `.studio/ideas.json`.

## Диагностика

Бейдж **⚠ N** открывает панель с группировкой по уровню и фильтром по коду и
тексту. Жёлтые пометки помечены как «неточность». «Копировать всё» отдаёт
markdown-список. Коды — в [troubleshooting.md](troubleshooting.md).

## Лог

`.studio/studio.log` — журнал сканов, ошибок и записи. HTTP-запросы по
умолчанию не пишутся; `studio dev --verbose` добавляет их. Удаление `.studio/`
стирает `metadata.json` безвозвратно: граф пересоберётся, описания — нет.
Поэтому `.studio/metadata.json` по умолчанию не игнорируется в git и
коммитится вместе с проектом; игнорируются только `graph.json`, `studio.log`,
`agent-brief.md`, `briefs/` и `last-brief.json`.
