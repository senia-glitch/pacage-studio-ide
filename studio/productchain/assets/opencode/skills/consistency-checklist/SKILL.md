# Чек-лист согласованности

Критик смотрел на пункты по одному. Ты смотришь, **складываются ли они в один продукт**.

## Сначала построй опору

1. **Словарь** (`glossary`): каждое ключевое понятие — один термин, определение, `forbidden_synonyms` (как его называть нельзя).
2. **Сущности** (`entities`): объекты, которые создаются и меняются (запись, заказ, клиент), и их состояния. Пройди требования: каждый переход состояния должен быть кем-то выполним.
3. **Сквозные пути** (`journeys`): для каждой роли варианта 1-4 главных пути от входа до результата, каждый шаг ссылается на требование. Путь, который нельзя собрать из требований, — уже находка.

## Проверки

| check | Ошибка |
|---|---|
| `glossary` | одно понятие названо по-разному |
| `roles` | роль в требованиях есть, а в варианте нет, или наоборот |
| `journey` | путь рвётся: нет шага, тупик, нельзя вернуться или исправить |
| `entity` | сущность создаётся, но не меняется/не отменяется; состояние, в которое нельзя попасть |
| `pattern` | списки, поиск, фильтры, уведомления, ошибки устроены по-разному без причины |
| `navigation` | к функции нельзя попасть из пути ни одной роли |
| `contradiction` | два требования исключают друг друга |

Пиши замечания в `remarks.json` (step 7). Исправляют требования аналитик; словарь, сущности и пути ведёшь ты.

## Признак хорошего результата

По сквозным путям можно провести человека по продукту без единого «а здесь непонятно, куда дальше». Эти пути потом станут тестами фронтенда.
